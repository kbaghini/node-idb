# Reliability and memory review — 2026-09-07

Comparison against commit `eeb2dc3978cd4a9fde7fb177f1b2a2b407a22aaf`
(`0.3.0`), using the updated working tree with 256-document internal write
batches. No storage-format migration or dependency change is required.

## Measurements

Windows x64, Intel Core i9-13900H, Node.js 24.11.1, SQLite 3.52.0.
Each workload ran three times per version, alternating before/after in fresh
Node processes and fresh temporary disk directories. Both versions used
`fieldIndexes: 'none'`, `durability: 'balanced'`, and unchanged cache defaults.
Values below are medians, not production capacity guarantees.

| Workload / metric | Before | After |
| --- | ---: | ---: |
| Ordered scalar stream, 12,000 rows | 3,220 ms | 538 ms |
| One INSERT of 12,000 small documents | 439 ms | 384 ms |
| One INSERT of 4,000 large documents | 875 ms | 856 ms |
| Large INSERT sampled peak RSS | 184.9 MiB | 129.1 MiB |
| Large INSERT sampled peak JS heap used | 94.4 MiB | 41.2 MiB |

The ordered stream was about 6 times faster in this specific test. Large-write
RSS was about 30% lower; sampled JavaScript heap was about 56% lower. The small
write-time difference for large documents is within ordinary run variability.
An earlier 64-document batch experiment used less memory but increased SQL-call
overhead; 256 was selected as a compromise. Very wide or large individual
documents can still use substantial memory.

The scalar-stream fixture inserted documents shaped as
`{ id, payload: ['z'.repeat(32)] }` for IDs 0 through 11,999, then consumed
`SELECT id FROM items ORDER BY id + 0` with `batchSize: 100`, checking every ID
and the final count. The arithmetic ordering deliberately exercises a sort
without a predicate index. The large-write fixture used 4,000 documents of
the same shape, with a shared 16,384-character input string, in one INSERT.
Process memory was sampled every 5 ms during that INSERT, including baseline
and completion. Native SQLite allocations, caller input, and GC are included;
sampling can miss short-lived peaks. The stream fixture's stored memory values
are only insertion boundary observations and are not stream memory peaks.

[Raw comparison measurements](2026-09-07-comparison.json) retain all runs.
The main benchmark now offers repeatable stream, memory, and slow-reader phases;
see the [benchmark guide](../README.md). Its memory sampling interval is 10 ms.

## Behavior and verification

- Cancellation before COMMIT dispatch rolls back mutations; after dispatch,
  the actual SQLite commit result wins over a late cancellation.
- Streams step one prepared statement and finalize it on completion, early
  return, failure, and cancellation while backpressured.
- Payload UPDATE preserves quoted collection identifiers.
- Encoding and SQL buffers are bounded by an internal 256-document batch;
  all batches share one transaction, including rollback of main/blob data.
- `sqliteCache` exposes per-collection main/blob KiB budgets and a main mmap
  limit, with readonly support, validation, public types, and diagnostics.
- Benchmark JSON format 2 records stream throughput, time to first row,
  same-engine queued-write latency, and sampled process memory.

Focused regression coverage includes pre-commit cancellation, late cancellation,
commit failure, volatile ordering, parameterized LIMIT/OFFSET, early stream
return, cursor failure, a paused consumer, rollback after multiple write batches,
cache eviction, readonly immutability, and benchmark JSON output. One existing
backup test now triggers cancellation after its fake backup handle is created,
instead of relying on a 10 ms filesystem timing assumption.

Final local validation: all 151 runtime tests and the TypeScript declaration
checks passed on Windows / Node.js 24.11.1. The seven-phase quick benchmark
completed; its report is [available here](2026-09-07-quick.json). Other CI
platforms and Node versions were not run locally.
